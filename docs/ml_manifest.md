# 1. Предыстория
Телекоммуникационная компания испытывает проблему оттока клиентов: ежемесячно 6–8% абонентов расторгают контракт и переходят к конкурентам. Привлечение нового клиента обходится в 5–7 раз дороже, чем удержание существующего. Бизнес хочет заранее выявлять клиентов с высоким риском оттока, чтобы направлять им персонализированные retention-предложения через CRM.

## 2. Ценностное предложение
Продукт позволяет:
- **Удерживать клиентов** — выявлять риск оттока и активировать retention-сценарии.
- **Снизить потери выручки** — потенциальная экономия при удержании клиентов из группы риска.
- **Автоматизировать решение** — ML-модель заменяет ручной анализ еженедельным автоматическим скорингом.

## 3. Цели
- Еженедельно предсказывать вероятность оттока для каждого активного клиента
- Передавать список клиентов группы риска (P(churn) > 0.4) в CRM через API
- Автоматически переобучать модель при деградации качества (ROC-AUC < 0.78)
- Обеспечить прозрачность: каждое предсказание должно содержать топ-3 причины

## 4. Решение
**Архитектура:** Batch-архитектура с автоматическим переобучением по расписанию (MLOps Level 2).

**Компоненты:**
- **Feature Store (Redis + PostgreSQL):** хранение признаков клиентов, версионирование фич
- **ML Pipeline Orchestrator (Apache Airflow):** DAG-и для ETL, обучения, валидации, деплоя
- **Model Registry (MLflow):** версионирование моделей, хранение метрик, артефактов
- **Serving API (FastAPI + Docker):** эндпоинт `/predict` для batch-предсказаний
- **Monitoring (Evidently AI + Grafana + Prometheus):** drift-детекция, мониторинг метрик
- **CI/CD (GitHub Actions + Tofu):** автоматический деплой инфраструктуры и кода
- **Инфраструктура:** VPS Beget (Ubuntu 24.04), оркестрация через Docker Compose

**Уровень ML-системы 2:**  
Полная автоматизация пайплайна переобучения и деплоя через CI/CD. При деградации модели Airflow-триггер запускает переобучение, MLflow фиксирует эксперимент, GitHub Actions деплоит новую версию на VPS через SSH + Docker Compose rolling restart.

## 5. Осуществимость
- Датасет: Customer Churn (Kaggle / IBM GitHub, 7043 записи, 21 признак)
- Облачная инфраструктура: VPS Beget, тариф 2 CPU / 4 GB RAM / 30 GB SSD
- Инструменты MLOps: Open-source: Airflow, MLflow, Evidently, FastAPI, Prometheus, Grafana
- Компетенции: Python, Docker, Docker Compose, OpenTofu
- Время на разработку: 3 недели

## 6. Данные
**Источник обучения:** [Telco Customer Churn Dataset](https://www.kaggle.com/datasets/blastchar/telco-customer-churn) — исторические данные биллинговой системы: демография, тип контракта, сервисы, платежи, факт оттока. Датасет также доступен напрямую через [IBM GitHub](https://raw.githubusercontent.com/IBM/telco-customer-churn-on-icp4d/master/data/Telco-Customer-Churn.csv) без регистрации. Набор данных был создан IBM как пример для обучения специалистов по анализу данных.

**Продуктовые данные (prod):** Еженедельный CSV-экспорт из биллинговой БД, загружается в директорию `data/` на VPS. Данные анонимизированы, PII-поля хешированы.

**Разметка:** Бинарная метка `Churn` (Yes/No) — факт расторжения контракта в течение следующих 30 дней. Разметка автоматическая из биллинга.

**Хранение признаков:** Feature Store на базе PostgreSQL (персистентное хранение) + Redis (кэш для быстрого получения признаков при инференсе). Оба сервиса развёрнуты в Docker Compose на том же VPS.

## 7. Метрики
**Retention rate** (доля удержанных из группы риска) ≥ 25%
**Выручка под защитой** (ARPU × удержанные клиенты) +3 млн руб./квартал
**Покрытие группы риска** (доля оттоков, попавших в топ-скоринг) ≥ 70%

## 8. Оценка качества модели
**Офлайн-метрики:**

| Метрика | Пороговое значение | Обоснование |
|---------|-------------------|-------------|
| ROC-AUC | ≥ 0.80 | Основная метрика ранжирования |
| Precision@top20% | ≥ 0.55 | Качество топ-сегмента для CRM |
| Recall | ≥ 0.65 | Не пропускать реальные оттоки |
| F1-score | ≥ 0.60 | Баланс |

**Онлайн-метрики (мониторинг):**

| Метрика | Пороговое значение |
|---------|-------------------|
| PSI (Population Stability Index) | < 0.2 (drift alarm) |
| Доля предсказаний P > 0.4 (% группы риска) | 5–15% (норма) |
| API latency P95 | < 500 мс |
| Процент ошибок API | < 1% |

## 9. Подбор модели
**Итерация 1:** Logistic Regression (интерпретируемость, быстрое обучение).  
**Итерация 2:** LightGBM (табличные данные, высокая точность).  
**Итерация 3:** LightGBM + Optuna (гиперпараметрический поиск).  

Модели сравниваются в MLflow по ROC-AUC на тесте. Определяется автоматически — побеждает только при улучшении ROC-AUC ≥ 0.01.

## 10. Инференс
**Тип:** Batch inference.  
**Расписание:** Каждое воскресенье в 02:00 UTC (Airflow CronTrigger).  
**Процесс:**
1. Airflow читает новые данные из директории `data/` на VPS.
2. Признаки вычисляются и кэшируются в Feature Store (PostgreSQL + Redis).
3. Модель из MLflow Registry применяется к батчу.
4. Результаты записываются в таблицу `churn_scores` (PostgreSQL) и передаются в CRM через webhook.

## 11. Обратная связь
**Биллинговая система** — фактический отток через 30 дней → автоматическое обновление разметки.
**CRM** — статус retention-предложения (принято/отклонено) → proxy-метрика качества скоринга.
**Мониторинг дрейфа** — Evidently AI еженедельно проверяет PSI и data drift, при PSI ≥ 0.20 отправляет триггер переобучения в Airflow через REST API.

**MDD (Metrics Driven Development):** Все архитектурные решения принимаются на основе статистических тестов (см. ADR-001). Переход к новой версии модели — только при статистически значимом улучшении метрик.
