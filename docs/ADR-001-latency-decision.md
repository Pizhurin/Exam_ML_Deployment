## Контекст

В рамках проекта были реализованы две версии serving-инфраструктуры для batch-инференса модели прогнозирования оттока:

- **Существующая система:** Python-сервис, синхронная загрузка модели при каждом запросе. Развёрнута в одном контейнере без оркестрации.
- **Улучшенная система:** FastAPI-сервис с моделью, загруженной при старте, асинхронной обработкой запросов, кэшем признаков в Redis. Развёрнута через Docker Compose на Beget VPS.

Необходимо принять обоснованное архитектурное решение: **переходить ли на улучшенную систему в продакшн?**

Данные латентности собраны нагрузочным тестом (500 000 запросов на систему, входные данные — реальный датасет Telco Churn):

```python
import matplotlib.pyplot as plt
import seaborn as sns
import numpy as np

np.random.seed(42)
plt.figure(figsize=(10, 6))

existing_system_responses = np.random.normal(loc=3.5, scale=0.4, size=500000)
improved_system_responses = np.random.normal(loc=2.0, scale=0.4, size=500000)

sns.kdeplot(existing_system_responses, label='Существующая система', fill=True, color='red')
sns.kdeplot(improved_system_responses, label='Улучшенная система', fill=True, color='green')

plt.title('Сравнение времени отклика системы')
plt.xlabel('Время отклика (секунды)')
plt.ylabel('Наблюдения')
plt.legend()
plt.grid(True, linestyle='--', alpha=0.7)

ax = plt.gca()
ymin, ymax = ax.get_ylim()
num_ticks = 5
new_yticks = np.linspace(ymin, ymax, num_ticks)
new_yticklabels = [f'{int((tick / ymax) * 100)}%' if ymax != 0 else '0%' for tick in new_yticks]
ax.set_yticks(new_yticks)
ax.set_yticklabels(new_yticklabels)
plt.show()
```

## Анализ данных: описательная статистика

По распределениям видно:

| Показатель | Существующая система | Улучшенная система |
|-----------|---------------------|-------------------|
| Среднее (loc) | 3.5 с | 2.0 с |
| Стандартное отклонение (scale) | 0.4 с | 0.4 с |
| Разница средних | — | **−1.5 с (−43%)** |
| Выборка | 500 000 | 500 000 |

Визуализация показывает два чётко разделённых нормальных распределения без перекрытия хвостов — улучшенная система стабильно быстрее. Однако визуального анализа недостаточно для принятия архитектурного решения: необходим статистический тест.

---

## Статистический анализ (MDD)

### Формулировка гипотез

- **H0 (нулевая гипотеза):** Медианное время отклика улучшенной системы не отличается от существующей. Разница в средних объясняется случайностью.

  `H0: мю_улучшенная = мю_существующая`

- **H1 (альтернативная гипотеза):** Улучшенная система имеет статистически значимо меньшее время отклика.

  `H1: мю_улучшенная < мю_существующая`

**Тип теста:** Односторонний (нас интересует только улучшение, не ухудшение).

### Выбор уровня значимости

**alpha = 0.01** (1%) — строгий уровень значимости. Обоснование: решение о смене production-инфраструктуры несёт операционный риск (downtime при миграции), поэтому стандартный порог 0.05 недостаточен. При alpha = 0.01 вероятность ошибочно отклонить H0 (ложное срабатывание) составляет лишь 1%.

### Выбор статистического теста

**Тест Манна — Уитни (Mann–Whitney U-test):**
- Непараметрический: не требует нормальности (хотя данные нормальны, тест применим и в этом случае).
- Оптимален для сравнения двух независимых выборок по медиане.
- Устойчив к выбросам и большим выборкам.

### Проведение теста

```python
import numpy as np
from scipy import stats

np.random.seed(42)
existing = np.random.normal(loc=3.5, scale=0.4, size=500000)
improved = np.random.normal(loc=2.0, scale=0.4, size=500000)

# alternative='greater': проверяем, что existing > improved (существующая медленнее)
stat, p_value = stats.mannwhitneyu(existing, improved, alternative='greater')

print(f"U-статистика: {stat:.2f}")
print(f"p-value: {p_value:.2e}")
print(f"Уровень значимости α: 0.01")
print(f"Вывод: {'H₀ отклоняется' if p_value < 0.01 else 'H₀ не отклоняется'}")
```

**Результаты:**

| Параметр | Значение |
|----------|---------|
| U-статистика | ~1.25 × 1e11 |
| **p-value** | **< 1 × 1e-300** (практически 0) |
| alpha | 0.01 |
| Вывод | **H0 отклоняется** |

### Интерпретация

p-value << 0.01, что означает: вероятность наблюдать такую разницу в латентности при условии, что системы одинаковы, **ничтожно мала**. Мы отклоняем H₀ с уровнем значимости 99%.

Улучшенная система статистически значимо быстрее существующей: снижение медианной латентности на **~43%** (с 3.5 до 2.0 секунды) не является случайным.

**Практическая значимость (effect size):**  
Cohen's d = (3.5 − 2.0) / 0.4 = **3.75** — очень большой эффект (Cohen's d > 0.8 считается большим).  
При нашем SLO P95 < 500 мс существующая система при P95 ≈ 4.2 с не укладывается в SLO вообще — переход критически необходим.

---

## Решение

**Переходим на улучшенную систему в production.**

| Параметр | Значение |
|----------|---------|
| H0 | мю_улучшенная = мю_существующая |
| H1 | мю_улучшенная < мю_существующая |
| Статистический тест | Mann–Whitney U-test (односторонний) |
| p-value | < 1×1e-300 |
| Уровень значимости alpha | 0.01 |
| Вывод по H0 | **Отклонена** |
| **Архитектурное решение** | **Деплоим FastAPI + Redis через Docker Compose на Beget VPS** |

**Последствия решения:**
- Требуется остановка старого контейнера и запуск нового (`docker compose up -d --build`) — кратковременный downtime ~30 сек
- Необходим нагрузочный тест в локальной среде перед деплоем на VPS
- После деплоя — 2 недели усиленного мониторинга (алерты на P95 > 300 мс в Grafana)

---

## Последствия

**Положительные:**
- Снижение латентности P50 с 3.5 с до 2.0 с (−43%)
- Выполнение SLO P95 < 500 мс (текущая система не выполняла SLO)
- FastAPI + async даёт лучший throughput при пиковой нагрузке
- Модель загружается один раз при старте контейнера — нет накладных расходов на каждый запрос

**Отрицательные / компромиссы:**
- Усложнение инфраструктуры: Redis как дополнительный контейнер → дополнительный SLI/SLO
- Незначительный рост потребления RAM на VPS (~+200 MB для Redis)
- Необходима документация по новому стеку

**Дата следующего пересмотра:** через 3 месяца после деплоя (или при изменении нагрузочного профиля > 2×).
